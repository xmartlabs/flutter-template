# Dependency Update PR

Stage 5: pushes the branch `dependency-update-apply` produced for one tier
(after `dependency-doc-sync` has had its turn on the same branch) and opens a
PR describing it. Never re-verifies anything — it only operates on candidates
`dependency-update-apply` already applied and confirmed with
`./scripts/checks.sh` (and codegen-cleanliness) on the real branch. Schema
lives in `../dependency-audit/references/report-schema.md`; don't restate
it here.

## Precondition

Refuse to open a PR for any candidate that doesn't have a `verdict` in
`verdicts.json` at all — a missing verdict means it never passed
`dependency-update-audit` and has no business being on an applied branch.
Treat this as a pipeline integrity failure, not something to paper over.

## Scope: one PR per branch

Each `dependency-update-apply` branch is exactly one tier
(`safe`|`review`|`breaking`) and one `kind`. Open exactly one PR per branch;
never combine two branches into one PR.

## Workflow

1. Push the branch: `git push -u origin <branch>`.
2. Title: conventional-commit prefix per
   `.github/pr-title-checker-config.json` (`fix: `, `feat: `, `docs: `,
   `refactor: `, `test: `, `chore: ` — enforced by the `pr-title-checker`
   action). A dependency bump is `chore: `, matching
   `dependency-update-apply`'s commit message, e.g.
   `chore: bump dio 5.4.3+1 → 5.9.0` or
   `chore: bump safe dependencies (4 packages)`.
3. Body: render from `references/pr-template.md`, filling every placeholder
   from `verdicts.json` for exactly the candidates on this branch. If a
   field has no data (e.g. no advisories), state that explicitly rather
   than deleting the row.
4. Open with `gh pr create --title "<title>" --body "<rendered body>"`.
   - `breaking` tier: always add `--draft`, and fill in the template's
     migration-checklist section — never opened ready-to-merge.
   - `safe` and `review` tiers: normal (non-draft) PRs.
5. Body must end, verbatim: `🤖 This PR was generated by an automated dependency-maintenance agent. Review before merging.`

## What goes in the body

Pull every field from the candidate records on this branch, not from memory:

- Summary row per candidate: package/component, `manifest` (or the
  toolchain adapter's full `version_file(s)` set), `current` →
  `latest_compatible`/target, `bump`, `urgency`, `risk`.
- What changed and why: `breaking_changes` per candidate, plus
  `changelog_url` (packages) or `migration_guide_source` (toolchain).
- What was verified: the actual `evidence` — `evidence.checks`,
  `evidence.codegen_clean`, a relevant `evidence.log` excerpt — from the
  real-branch re-verification, not a restated claim. Evidence, not
  assertions, mirroring `dependency-update-audit`'s own discipline.
- Affected call sites: `affected_call_sites` for any candidate where it's
  non-empty.
- Docs updated: `dependency-doc-sync`'s report for this branch — the files it
  touched and what changed in each, or "None needed this run."
- Human checklist: every `safe-with-refactor` candidate ("review the
  mechanical diff — see evidence.log") and any never-auto-update package in
  this tier (regen diff needs manual review regardless of verdict).

## Notes

- A toolchain PR's summary should also surface the adapter's
  `native_project_impacts` and `ci_impacts` (e.g. `flutter.md`'s worked
  example) — the real blast radius, not just the version-file diff.
- If `dependency-update-apply` reported it stopped early on this branch
  (verification failed mid-run), don't open a PR — report the discrepancy
  instead; this skill only ships branches that finished cleanly.
